1. CORE PRINCIPLES & COLLABORATION RULES
================================================================================
1. SINGLE OWNERSHIP PER MODULE: Each module and file has one designated primary
   owner. Collaborators may review or integrate, but must not make uncoordinated
   commits directly to another member's files.
2. NO REBUILDING WORKING FEATURES: All core features (3D Globe, Shelters, Map,
   Reporting, Gemini AI, MongoDB Atlas, Auth) are already implemented and working.
   Members are tasked with enhancements, hardening, testing, and presentation.
3. ISOLATE FEATURE BRANCHES: Never commit directly to 'main' or 'master'. Always
   work on a descriptive feature branch (e.g., 'feat/member1-frontend-polish').
4. SYNCHRONIZE SHARED FILES: Shared files ('combined/script.js', 'backend/server.js')
   require explicit verbal/chat communication before editing to prevent race conditions.
5. ZERO SECRETS IN GIT: Never commit '.env' or active API keys. Use '.env.example'
   with safe placeholder variables.

6. PROPOSED GITHUB COLLABORATION WORKFLOW (STEP-BY-STEP)
================================================================================

Step 1: Synchronize with the Latest Main Branch
Before beginning any new work, update your local repository:
$ git checkout main
$ git pull origin main

Step 2: Create a Feature Branch
Never work directly on main. Create and switch to your assigned feature branch:
$ git checkout -b feat/member1-ui-ux-enhancements
(or your respective branch name)

Step 3: Make Focused, Modular Changes
Work only on your assigned files. Test your changes locally before staging:
# Check which files have been modified:
$ git status

Step 4: Commit with Standardized Commit Messages
Stage only the files you intentionally modified:
$ git add combined/index.html combined/CSS/index.css
$ git commit -m "feat(ui): optimize home hero typography and responsive metrics"

Use conventional commit prefixes:
- feat: New feature or capability
- fix: Bug fix
- docs: Documentation changes
- style: Formatting, CSS polish
- test: Adding or updating tests
- refactor: Code cleanup without logic change

Step 5: Rebase on Latest Main Prior to Push
Ensure your branch is up to date with teammates' merged work:
$ git fetch origin
$ git rebase origin/main
(Resolve any merge conflicts if they occur, then 'git rebase --continue')

Step 6: Push Your Feature Branch to GitHub
$ git push -u origin feat/member1-ui-ux-enhancements

Step 7: Open a Pull Request (PR)
1. Go to your repository on GitHub.
2. Click "Compare & pull request".
3. Title your PR clearly: "[FEAT] Member 1: Mobile UI/UX polish".
4. Add a concise description of what was changed and how to test it.
5. Request review from at least one teammate (e.g., Member 4 or Member 3).

Step 8: Review, Approve, and Merge
1. Reviewer checks code diff for accidental changes, syntax errors, or secrets.
2. Once approved, use "Squash and Merge" or standard Merge.
3. Delete the remote feature branch after successful merge.

7. HOW TO AVOID MERGE CONFLICTS ON SHARED FILES
================================================================================
Certain files are inherently shared across disciplines:
- 'combined/script.js' (Global router, auth guards, header builder)
- 'backend/server.js' (Express route registry)
- 'combined/reports-store.js' (Central data store)

TO PREVENT CONFLICTS:
1. INFORM FIRST: Before editing a shared file, post a message in your team chat:
   "Member 2 editing server.js lines 120-170 for Gemini prompts. Please avoid server.js for 30m."
2. MODULAR EXTENSIONS: When adding a new capability, prefer creating a dedicated
   sub-module (e.g. 'combined/shelters.js', 'combined/globe.js') and importing it
   into the main script with a single line, rather than appending hundreds of lines.
3. SECTION ISOLATION: Keep clear line boundaries:
   - Lines 1-246 in server.js: AI & Meteorological proxies (Member 2)
   - Lines 247-693 in server.js: Database & Auth endpoints (Member 3)
   - Do not reformat or auto-indent code blocks outside your assigned section.
4. PULL FREQUENTLY: Run 'git pull origin main' regularly so your local branch never
   strays more than a few commits behind the team.
